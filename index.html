kvstore

github.com/daen8584-spec/kvstore

An in-memory key-value server in C++20 that speaks the Redis protocol, so existing Redis clients and tools work with it unchanged.

  • C++20
  • Linux epoll
  • Networking
  • Transactions
  • Persistence
  • Sanitizers
  • Fuzzing
  • Docker
0.86 to 1.18×throughput relative to Redis on the same machine, without pipelining
83commands across strings, lists, hashes, sets, sorted sets and transactions
71protocol and command tests that pass unchanged against both kvstore and Redis 7.0
0.94median write throughput kept with 10,000 watched keys, up from 0.81 to 0.86

Engineering decisions

  • A single-threaded event loop with no locks on the data path, fair reading across clients and backpressure for clients that do not read their replies.
  • Transactions with MULTI, EXEC and optimistic locking with WATCH. Write commands declare their key positions, and a transaction is logged as one block, so a crash keeps all of it or none.
  • Random and derived writes (SPOP, SINTERSTORE) are logged as their effect, so replaying the append-only file is deterministic.
  • The hash table resizes incrementally, so a resize never stalls a request, and keys are hashed with SipHash and a random key against hash flooding.
  • Append-only persistence with configurable fsync, recovery from a truncated file, and compaction in a forked child while the server keeps serving. Replies wait until the write is in the file.
  • Verified with AddressSanitizer, UndefinedBehaviorSanitizer and fuzzing that checks every command produces exactly one well-formed reply.

hybrid-search

github.com/daen8584-spec/hybrid-search

A retrieval service for RAG that combines BM25 keyword search and vector search inside PostgreSQL and merges them with Reciprocal Rank Fusion, evaluated on the BEIR SciFact benchmark.

  • Python
  • FastAPI
  • PostgreSQL
  • pgvector
  • Embeddings
  • Evaluation
  • Docker
  • mypy strict
0.719nDCG@10 for hybrid search, above BM25 (0.688) and vector search (0.700) alone
0.958Recall@100 for hybrid search, against 0.918 and 0.928 for each retriever alone
18 msmedian retrieval and fusion latency for the top 100 documents
−36%embedding provider calls with the cache shared by four API processes

Engineering decisions

  • One datastore: documents, chunks, the inverted index and the vector index live in PostgreSQL and are updated in one transaction.
  • BM25 implemented in SQL over an inverted index with covering indexes, replacing built-in full-text ranking that made hybrid search worse than vector search alone.
  • Fusion weights and reranking are tuned on a separate query split, so the reported test scores are not fitted to the test set. A reranker that gained less than the noise ships as an option, not the default.
  • Query embeddings are cached in memory and in an unlogged PostgreSQL table shared by every API process, bounded by expiry and row limits, and never able to fail a search.
  • Ingestion is incremental: unchanged documents are skipped and unchanged chunks reuse their stored embeddings.

DocExtract

github.com/daen8584-spec/docextract

Full-stack document extraction: an LLM pulls structured fields from uploaded text, PDF and scanned documents, and a human reviewer verifies, corrects and approves them before they are trusted.

  • TypeScript
  • Next.js
  • PostgreSQL
  • Drizzle ORM
  • Zod
  • LLM integration
  • Tesseract OCR
  • Docker
100%field accuracy on a 20-case evaluation set, including 10 targeted failure modes
0hallucinated values across the evaluation set
0.4%OCR character error rate on rendered scans of the evaluation cases
97unit and integration tests, the integration tests against real PostgreSQL and Tesseract

Engineering decisions

  • Model output is treated as untrusted input: every response is validated against a schema, and an invalid response is retried with backoff instead of being stored.
  • A document, its audit event and its extraction job are written in one transaction, so a document can never exist without the job that processes it. Workers claim jobs with FOR UPDATE SKIP LOCKED and recover from crashes.
  • Scanned PDFs are read by OCR in the worker, and the text is committed before extraction, so a retried extraction never repeats OCR. Low OCR confidence is flagged to the reviewer.
  • Authorization is checked per object, with three roles and server-side sessions. Status transitions are atomic, so two reviewers cannot approve conflicting versions.
  • An evaluation command fails when field accuracy drops below a threshold, so prompt and model changes are checked before they ship.

Investigations

Numbers that disagreed with the design, and what finding the cause changed. Each is written up with its measurements in the linked decision record.

A 42 ns lookup that cost 15% of throughput

Optimistic locking made every write check whether its key was watched. With 10,000 watched keys, pipelined write throughput fell to 0.81 to 0.86 of normal. The lookup took 42 ns in isolation, and my first fix, a counter filter in front of it, changed nothing. Timing it inside the running server showed 266 ns: the rest of the server evicted it from the CPU cache. A 32 KiB bit filter that stays cached brought throughput back to a median of 0.94.

kvstore ADR 0009

OCR that silently dropped the invoice total

Measuring OCR on scans of the evaluation invoices showed a 2% character error rate, and one document had lost its TOTAL DUE line entirely: Tesseract's default layout analysis read the dot leaders as layout. It also turned the apostrophe in the Swiss amount 12'463.93 into a typographic one. A different page segmentation mode and quote normalization brought the error rate to 0.4 to 0.5%, with both lines intact.

DocExtract ADR 0008

Keyword search that made hybrid search worse

The first benchmark run scored hybrid search below vector search alone: 0.602 against 0.700 nDCG@10. PostgreSQL's built-in ranking has no inverse document frequency, so common words counted as much as rare ones. BM25 over an inverted index in SQL raised keyword search from 0.399 to 0.688 and its latency fell from 374 ms to 22 ms, putting hybrid search above both retrievers.

hybrid-search ADR 0007

A one-line request that stalls Redis

Checking set commands against Redis 7.0.15, SRANDMEMBER key -4611686018427387904 made Redis stop responding while it built a reply of that many members. kvstore bounds the count and documents the difference, with a test.

How I work

The habits behind the work above.

Measure before claiming

I check behaviour against a reference rather than assuming it. When a measurement exposes a weakness, the fix and the before and after numbers go into the documentation, including what did not work.

Prefer the boring solution

PostgreSQL for queues, rate limits, search and caching before adding another service. Complexity has to earn its place with a measured gain.

Design for failure

Every multi-step operation has a defined outcome when it is interrupted: a crash, a timeout, a full disk or a retry must leave the data consistent.

Write decisions down

Significant decisions and their trade-offs go into architecture decision records, so reviewers can check them against their own assumptions and future maintainers know why.

Lead the agents, own the result

I direct AI coding agents with clear specifications and context, then review their output for correctness, security and data integrity before anything ships.

Make work reviewable

Small changes with descriptions that state the behaviour, the design, the evidence and the limits, so a reviewer can say yes or no quickly.
