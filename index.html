Full-stack document extraction: an LLM pulls structured fields from uploaded text and PDF files, and a human reviewer verifies, corrects and approves them before they are trusted.

Engineering decisions

  • Model output is treated as untrusted input: every response is validated against a schema, and an invalid response is retried with backoff instead of being stored.
  • A document, its audit event and its extraction job are written in one transaction, so a document can never exist without the job that processes it. Workers claim jobs with FOR UPDATE SKIP LOCKED and recover from crashes.
  • Authorization is checked per object, with three roles and server-side sessions. Status transitions are atomic, so two reviewers cannot approve conflicting versions.
  • Rate limiting for login, signup and upload uses token buckets in PostgreSQL, so limits hold across any number of app instances without adding Redis.
  • The evaluation harness can fail CI when accuracy drops, so a prompt or model change cannot silently make extraction worse.

hybrid-search

github.com/daen8584-spec/hybrid-search

A retrieval service for RAG that combines BM25 keyword search and vector search inside PostgreSQL and merges them with Reciprocal Rank Fusion, evaluated on the BEIR SciFact benchmark.

0.719nDCG@10 for hybrid search, above BM25 (0.688) and vector search (0.700) alone
0.958Recall@100 for hybrid search, against 0.918 and 0.928 for each retriever alone
18 msmedian retrieval and fusion latency for the top 100 documents
0.665BM25 nDCG@10 on SciFact reported in the BEIR paper, for reference

What the first measurement changedThe first evaluation showed weak keyword ranking (nDCG@10 0.399) and revealed that the vector index settings were silently running exact search. I replaced the built-in ranking with BM25 over an inverted index in SQL (0.688) and tuned the index against exact search. A cross-encoder reranker gained less than the noise at about six seconds per query, so it ships as an option, not as the default.

Engineering decisions

  • One datastore: documents, chunks, the inverted index and the vector index live in PostgreSQL and are updated in one transaction.
  • Fusion weights and reranking are tuned on a separate query split, so the reported test scores are not fitted to the test set.
  • Ingestion is incremental: unchanged documents are skipped and unchanged chunks reuse their stored embeddings.

kvstore

github.com/daen8584-spec/kvstore

An in-memory key-value server in C++20 that speaks the Redis protocol, so existing Redis clients and tools work with it unchanged.

  • C++20
  • Linux epoll
  • Networking
  • Persistence
  • Sanitizers
  • Fuzzing
  • Docker
0.86 to 1.18xthroughput relative to Redis on the same machine, without pipelining
61commands across strings, lists, hashes and sorted sets
Redis 7 and 8the same integration tests pass against kvstore and real Redis

Engineering decisions

  • A single-threaded event loop with no locks on the data path, fair reading across clients and backpressure for clients that do not read their replies.
  • The hash table resizes incrementally, so a resize never stalls a single request, and keys are hashed with SipHash and a random key against hash flooding.
  • Append-only persistence with configurable fsync, recovery from a truncated file and compaction in a forked child while the server keeps serving.
  • Checked with AddressSanitizer, UndefinedBehaviorSanitizer and continuous fuzzing of the protocol parser in CI.
