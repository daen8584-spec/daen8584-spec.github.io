Hi, I'm a software engineer.

Most of what I enjoy is the part of software nobody sees when it works: what happens when the network drops, when a message arrives twice, when two people click "buy" at the same moment, or when a page has to load on a cheap phone with no signal.

I've worked across back end, front end, data and AI, mostly in TypeScript, Python and C++. I'm open to full-time, part-time, contract or freelance work, at any level.

Some things I've worked on

  • A checkout on Stripe where most of the work went into the edge cases. Stripe can send the same event twice, or in the wrong order. A customer can pay a second after their order expired. There's a test where 12 people try to buy the last 5 posters at the same time, and exactly 5 sell. Code · why it's built this way
  • A Redis-compatible database server in C++. When I added transactions, writes got about 15% slower, and my first fix didn't change anything. Timing it inside the running server showed a 42 ns lookup taking over 200 ns because of CPU cache misses. A small 32 KB filter got most of the speed back. Write-up
  • An invoice reader that uses an LLM and OCR, with a person checking the result before it's saved. Measuring the OCR on scanned invoices, I found it was silently dropping the line with the total, which is the one number that matters. A different Tesseract setting fixed it, and errors went from 2% to 0.5%. Code
  • Search for RAG systems that combines keyword and vector search in PostgreSQL. The first version made results worse than vector search alone. Rewriting the keyword ranking as BM25 in SQL made it both better and 17 times faster. Code
  • A climate dashboard that pulls CO₂ and temperature data from NOAA and NASA every Monday and checks it before publishing. If the data looks wrong, the old version stays up.
  • A budget app that works offline and installs on a phone. The tests ran on slow machines and caught a bug where it could lose what you were typing, so I fixed that before anyone used it.

There's also a small command-line tool for tidying up folders, which turned out to be a good lesson in how differently Windows handles file paths.

How I like to work

I measure before I change things, and I write tests that try to break the code rather than confirm it works. When I make a decision that someone might question later, I write down why, so the next person can change it without guessing.
